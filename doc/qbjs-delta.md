Deviations from QBJS
--------------------
Copied from boxgaming/qbjs commit `1589a46` (version 0.11.6), with local changes. Every change is marked with a `qb64-ide` comment in the source.

**Runtime (`qbjs/qb.js`)**
* `STRING$(n, code)` maps the code through the CP437 table like `CHR$` does, so `STRING$(10, 219)` draws blocks instead of `Û`.
* `RANDOM` files: `OPEN` creates or opens them with a record length (default 128). `GET`/`PUT` take record numbers (omitted means the next record), and `LOC`, `SEEK` and `EOF` work in records.
* `GET`/`PUT` read and write `STRING * n` values as exactly *n* bytes (padded with spaces, or truncated). In `RANDOM` files a variable-length string is stored as a 2-byte length plus its characters. `_INTEGER64` values are supported.
* Edge cases follow QB64, checked by comparing data files byte for byte with programs built by QB64:
  * only the record's data is written: the last record isn't padded, and old bytes after a shorter record stay;
  * a record larger than `LEN` raises "Bad record length" (QB64 error 59) and writes nothing;
  * a `GET` past the end returns zeroed values, sets `EOF` and leaves `LOC` on the record before.
* `QB.typeSize(type)` gives the byte size of a `TYPE`, for `LEN`.
* `QB.fixStr`, `QB.initFixStr` and `QB.copyRec` are used by compiled code for `STRING * n` values and record copies (below). `qbjs/qb-console.js`, the small runtime the command-line compiler runs on, has the same three.
* `ON ERROR` support: `QB.defineErrorHandler`, `QB.setErrorHandler` and `QB.handleError` (see the compiler notes), and the functions `ERR`, `ERL` (always 0, as QBJS has no line numbers), `_ERRORLINE` and `_ERRORMESSAGE$`. Runtime errors are given QBasic error numbers, for example 53 for "File not found", 59 for "Bad record length" and 62 for "Input past end of file". Errors without a QBasic equivalent are 5, "Illegal function call".
* `ERROR n` raises error *n* with its QBasic message, so a handler can catch it. Upstream always threw "Unhandled Error #n".
* `READ` past the end of the `DATA` raises "Out of DATA" (error 4). Upstream returned `undefined`. `DATA` is also cleared when a program starts, so a program without `DATA` can't read the previous program's.
* `CLOSE #n` of a file that isn't open does nothing, as in QBasic. Upstream raised "Invalid file handle".
* `PRINT #` keeps each file's column, so `TAB` and the comma's 14-character zones count from the start of the line, also after a `PRINT #` that ended with `;`. Upstream counted from the start of the last item, and its zones were uneven.
* `INPUT #` follows QBasic (programs only). The file is read as a stream, so values can continue on the next line, and the next `INPUT #` goes on from where the last one stopped. A number ends at a space, comma or line end; a string at a comma or line end, unless it is quoted; and a blank line is an empty value. The compiler tells the runtime which variables are numbers (`QB.sub_InputFromFile(fh, values, "NNS")`). Upstream read one line per `INPUT #` and split it at commas, so ` 637   561` could not be read as two numbers.
* `WRITE` and `WRITE #` write the value of each item (programs only): strings in quotes, numbers without spaces (`.5`, `-2.5`, `1E+20`). Upstream wrote the JavaScript text of anything but a plain variable, so `WRITE #1, -2.5` wrote `- 2.5` and `WRITE #1, x + 1` wrote ` x + 1`.
* `RUN ["program"]` (`QB.sub_Run`): closes all files and ends the program with a signal that the run loop catches (`qbjs/runner.js` `QBRunner.run`, called by `app.js` `runProgram`). The IDE then compiles and starts the program named, or the same one again. The name is relative to the current folder, and `.BAS` is added if there is no file without it. A missing file is "File not found" (error 53), which `ON ERROR` can catch. The new program starts with fresh variables and screen, in the folder that was current. Messages from it show its path.
* `QB.setSourceDecoder(fn)`: how `$INCLUDE` and `Import` read `.bas`, `.bi` and `.bm` files from the virtual file system (`QB.sub_Fetch`). `fn` gets the file's bytes and returns its text. `null` (the default, and what the IDE uses) reads one character per byte, as before. `QBRunner.run({ decodeSource })` sets it, and also uses it for programs started by `RUN "name"`. The embedded player passes a decoder that reads UTF-8, or code page 437 for files that aren't valid UTF-8, so box drawing and accents in a package's files come out as on a DOS screen.
* `COMMAND$` and `_COMMANDCOUNT` come from `QB.setCommand(args, name)`, which `QBRunner.run` calls for each run with its `args` option (the embedded player's `args` attribute or `qbjs.json`). `COMMAND$` is the whole text, `COMMAND$(n)` the *n*th argument (double quotes group words), `COMMAND$(0)` the program's path, as in QB64. Upstream always returned `""` and 0. In the IDE there are no arguments, so only `COMMAND$(0)` changes: it now gives the program's path.
* `_TITLE` goes to a handler set with `QB.setTitleHandler(fn)` (the embedded player reports it to the page instead of renaming its own hidden page), and `_TITLE$` returns the last title set. Without a handler (the IDE) it sets `document.title`, as before.
* `QB.downloadFile` (used by `FS.DownloadFile`) falls back to a download link when the save picker is refused with a `SecurityError`, as it is in a sandboxed or cross-origin frame. Cancelling the picker still cancels.
* `OPEN` finds the folder of a path relative to the current folder, and a missing folder is "Path not found" (error 76). Upstream looked from the root and fell back to the current folder. `OPEN ... FOR OUTPUT` empties an existing file whose name differs only in case, rather than adding a second one. `MKDIR` resolves its parent folder in the same way.
* `LINE INPUT #` and `INPUT #` move past CR+LF line endings. Upstream stopped on the LF, so after reading a line written by `PRINT #` the next read returned an empty line and `EOF` came one line late.
* `VIEW PRINT [top TO bottom]` (`QB.sub_ViewPrint`) sets the text window. `PRINT` and `INPUT` scroll only its rows, `CLS` and `CLS 2` clear only the window (`CLS` also clears the bottom row, `CLS 0` the whole screen), and `LOCATE` outside it is error 5. QB64 also allows the row just below the window. `VIEW PRINT` moves the cursor to the top row of the window. Rows outside the range, or top after bottom, are error 5. As in QBasic and QB64, the window starts as every row but the last, so text scrolls rows 1–24 and row 25 stays put. A new line on row 25 scrolls rows 1–24 and leaves the cursor on row 24. `VIEW PRINT` alone, or `VIEW PRINT 1 TO 25`, makes all 25 rows scroll. Upstream had no `VIEW PRINT` and scrolled all 25 rows. Checked against QB64 screen dumps (`tests/viewprint`).
* `CLS` empties the rows it clears for `SCREEN(row, col)`. Upstream left the old characters there. A line that wraps on the bottom row now scrolls once per wrap. Upstream scrolled the wrong row there.

**File system (`qbjs/vfs.js`)**
* Names ignore case, as in DOS. `findChild(folder, name)` looks for the exact name first, then one that differs only in case, and only ever returns files and folders, never node properties such as `parent`. `getNode` uses it, so `OPEN`, `CHDIR`, `KILL`, `NAME`, `RUN` and the rest all accept `name.dat` for `NAME.DAT`. The IDE's own name checks (New File, New Folder, Rename, Upload) ignore case too, so it won't create `A.TXT` beside `a.txt`, but a rename can still change only the case.
* A path starting with `..` goes up from the current folder. Upstream went to the root but went on looking in the current folder, so `..\SETTINGS.DAT` from a subfolder found the wrong file, or none.

**Compiler (`tools/qb2js.bas`, built into `qbjs/qb2js.js`)**
* Variable names follow QBasic: names that differ only by type suffix are different variables. `k`, `k$`, `k%`, `k#` and `k&` are five variables, `k!` is the same as `k`, and after `DIM x AS INTEGER`, `x` and `x%` are the same. A plain variable and an array may share a name (`a` and `a()`, `a$` and `a$()`). Upstream QBJS ignored suffixes, so all of these were one variable. In the JavaScript, a suffixed variable gets a type tag: `k$` is `k$s`, `k%` is `k$i`, `k#` is `k$d`, `k&` is `k$l`. If a plain variable and an array still share a name, the later one gets `$a` or `$v` added. A bare name is never an array, except in `UBOUND(a)` and `LBOUND(a)`. This applies to programs only. The compiler itself and imported QBJS libraries keep QBJS names, because their `$If Javascript` blocks use them.
* `DATA` follows QBasic. Each item is kept as text, and `READ` converts it to the type of its variable (`QB.readValue`). Unquoted items may contain spaces and `'` (`DATA Chain Mail, rabbit's foot`), and `'` and `REM` on a `DATA` line are data, not comments. A quoted item is kept exactly, an unquoted one is trimmed, an empty item reads as `""` or 0, and an unquoted `:` ends the statement. Upstream copied unquoted items into the JavaScript, so `DATA Chain Mail` made the whole program invalid. Like the variable names, this applies to programs only.
* One-line `IF` follows QBasic: everything after `THEN` on the line belongs to the `IF`, so `IF a THEN x: IF b THEN y` nests, and each `ELSE` belongs to the nearest `IF` without one. Upstream split the line at its last `IF`, which left blocks open ("IF without END IF", "FOR without NEXT"). The line is split on its own text, so `THEN`, `ELSE` and `:` inside strings are left alone. This applies to programs only.
* `SPC(n)` and `TAB(n)` in `PRINT` and `PRINT #`. Upstream compiled them as arrays named `SPC` and `TAB`. They are passed to the runtime as markers (`QB.printSpc`, `QB.printTab`). `TAB(n)` moves to column n, or to column n of the next line if the cursor is past it, and `SPC(n)` prints n spaces (n and the column are taken modulo the screen width). `PRINT` items written next to each other (`SPC(4) "text"`, `"Zorag"q$`) are printed as if `;` were between them.
* Empty arguments in `CIRCLE`, `PSET`, `PRESET` and `PAINT` (`CIRCLE (x, y), r, c, , , .5`) use the default. Upstream produced invalid JavaScript.
* `CONST` names with a type suffix work (programs only): `CONST TITLE$ = "Eamon"` is found by `TITLE$`, also inside a `SUB`, and becomes the JavaScript name `TITLE$cs` (`N%` becomes `N$ci`). Before, `TITLE$` in an expression was taken for a new, empty variable, and `CONST N% = 3` produced invalid JavaScript.
* `VIEW PRINT` and `VIEW PRINT top TO bottom` compile to `QB.sub_ViewPrint`. A graphics `VIEW` is still unsupported.
* `compile(src, true)` makes a debug build: the first statement of each line starts with `if (QB.dbgHit(line, file)) { await QB.dbgPause(line, file, (x) => eval(x)); }`, where *file* is `""` for the program and the `$INCLUDE` name for an include file. The arrow function lets the debugger read the variables in scope. A debug build also lists the variables of the main program and of each `SUB` and `FUNCTION` (`QB.dbgScopes`), names the scope in each hook, and gives the main program's own reader (`QB.dbgMain`), so its variables can be shown while a `SUB` runs.
* Each `$INCLUDE` file is a module of its own. Upstream changed the including file's module in place, so lines of an include before a nested `$INCLUDE` were reported (in messages) as being in the nested file.
* `DECLARE SUB` and `DECLARE FUNCTION` lines are accepted silently. QBJS doesn't need them; upstream warned on each one.
* `DIM a$(10)` and an array parameter `a$()` are string arrays. Upstream took the type from `a$(10)` and made them SINGLE.
* `OPEN file [FOR mode] [ACCESS ...] [LOCK ...] AS [#]n [LEN = reclen]`. Without `FOR` the mode is `RANDOM`. File names and file numbers can be expressions.
* `STRING * n` keeps its length in `TYPE` fields (both `x AS STRING * n` and `AS STRING * n x, y`) and in `DIM`. The lengths are passed to the runtime.
* `LEN(x)` of a `TYPE` variable, `TYPE` array element, `STRING * n` variable or `STRING * n` field returns the declared size. Upstream returned 15, the length of `"[object Object]"`.
* `GET`/`PUT` accept array elements (`team(i)`), fields (`r.score`, `team(i).name`) and undeclared variables (`GET #1, , n%`).
* `SEEK #n, pos` compiles. Upstream left the `#` in the JavaScript.
* A `STRING * n` variable, array element or field starts as *n* `CHR$(0)` characters, as in QB64. Storing a value in one (`=`, `READ`, `INPUT`, `LINE INPUT`, and their `#` file forms) pads it with spaces or cuts it to *n* characters.
* Assigning a `TYPE` value (`c = r`, `team(i) = r`, `r.pos = p`) copies the record, including nested `TYPE` fields. Upstream made both names refer to one JavaScript object. Passing a record to a `SUB` still passes it by reference, as in QBasic. When the compiler builds itself, records are not copied, because its own source relies on the shared objects.
* `GOTO label`, `GOSUB label`, `RETURN`, `RETURN label`, `ON n GOTO a, b, c`, `ON n GOSUB a, b, c`, `IF x THEN 100`, `IF x GOTO label` and line numbers (`10 PRINT "hi"`). Upstream QBJS has none of these. JavaScript has no `goto`, so a `SUB`, `FUNCTION` or main program that uses one of them is compiled as numbered sections inside a loop (`___d: for (;;) { switch (___pc) { case 0: ... } }`). A jump sets the section number and continues the loop. In that code, `IF`, `FOR`, `DO`, `WHILE`, `SELECT CASE`, `EXIT` and `_CONTINUE` are compiled as conditional jumps too, so a label can be anywhere, including inside a loop. `GOSUB` keeps its return points on a stack. Code without jumps compiles as before, and code with them ran a 20-million-iteration loop no slower than the normal QBJS loop.
* `ON ERROR GOTO label`, `ON ERROR GOTO 0`, `RESUME`, `RESUME 0`, `RESUME NEXT` and `RESUME label`. In QBasic a handler is ordinary main-program code, which can `GOSUB` and `GOTO` anywhere in the main program and run on into the code after it. So for each handler, the main program is compiled once more, as jumps, into a function that starts at the handler's label and shares the main program's variables; `RESUME` returns from it with what to do. The handler's code also stays in the main program, so a `GOTO` to its label works, and a `RESUME` reached that way is "RESUME without error" (error 20), as in QBasic. In ALDAAR.BAS (2,665 lines) the copy adds about 6% to the compiled program. In a program that uses `ON ERROR`, each statement is wrapped in a `try`/`catch` that calls the active handler and then runs the statement again or goes on to the next one. Programs without `ON ERROR` compile as before. Behaviour follows QB64:
  * an error in a `SUB` or `FUNCTION` goes to the handler, and `RESUME NEXT` continues inside the `SUB`;
  * a handler that runs off the end of the main program without `RESUME` ends the program;
  * an error inside a handler stops the program;
  * `ON ERROR GOTO 0` inside a handler turns error handling off but doesn't stop the program;
  * `RESUME label` after an error inside a `SUB` leaves the `SUB` and continues at the label in the main program.
* A label can be followed by a statement on the same line (`oops: PRINT ERR: RESUME NEXT`). Only names used by a `GOTO`, `GOSUB`, `RESUME` or `RESTORE` count as labels there, so `CLS: PRINT` is still two statements.
* `READ a, b, c` reads one value at a time, so if the `DATA` runs out at `c`, `a` and `b` are still set.

To rebuild the compiler after editing `tools/qb2js.bas`, run this twice from the project root. The second run checks that the new compiler compiles itself the same way:

```
node tools/qbc.js tools/qb2js.bas
```

To see the JavaScript for a program, run `node tools/qbc.js program.bas`.

To update QBJS, copy the same files from a newer checkout and re-apply the `qb64-ide` changes.
